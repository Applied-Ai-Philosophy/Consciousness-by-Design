## How to Contribute

### Before You Start

1. **Read the Framework**: Familiarize yourself with the [README](README.md) and [Executive Summary](docs/executive-summary.md)
2. **Understand the Theory**: Review the [Theory Overview](theory/README.md)
3. **Check Existing Issues**: See if your idea or question is already being discussed
4. **Start Small**: Begin with clarifications, typo fixes, or documentation improvements

## Types of Contributions

### 1. Research Findings

Share empirical results relevant to FNC predictions:

- **Experimental data** supporting or challenging FNC predictions
- **Replication studies** of proposed experiments
- **Novel measurements** of Field, Node, or Cockpit properties
- **Meta-analyses** relevant to consciousness research

**Use**: [Research Result Issue Template](.github/ISSUE_TEMPLATE/experimental-result.md)

### 2. Experimental Designs

Propose new experiments or refine existing protocols:

- **Novel experimental paradigms** to test FNC predictions
- **Improved measurement techniques** for Field coupling, Node coherence, or Cockpit rendering
- **Methodological refinements** to existing protocols
- **Cross-validation approaches** across different systems

**Use**: [Research Question Issue Template](.github/ISSUE_TEMPLATE/research-question.md)

### 3. Theoretical Refinements

Suggest improvements to the FNC framework:

- **Clarifications** of ambiguous concepts
- **Extensions** to handle new cases or systems
- **Formal models** of Field-Node-Cockpit interactions
- **Mathematical frameworks** for measuring consciousness properties
- **Critiques** identifying theoretical gaps or inconsistencies

**Use**: [Theoretical Refinement Issue Template](.github/ISSUE_TEMPLATE/theoretical-refinement.md)

### 4. Application Scenarios

Propose new applications or use cases:

- **Novel AI architectures** and their consciousness implications
- **Clinical protocols** for disorders of consciousness
- **BCI designs** preserving Cockpit integrity
- **Regulatory frameworks** for AI governance
- **Ethical analyses** of specific cases

**Use**: [Application Case Issue Template](.github/ISSUE_TEMPLATE/application-case.md)

### 5. Falsification Evidence

Report evidence that challenges FNC:

- **Experimental results** contradicting FNC predictions
- **Counterexamples** to FNC principles
- **Alternative explanations** for FNC-predicted phenomena
- **Logical inconsistencies** in the framework

**Use**: [Falsification Evidence Issue Template](.github/ISSUE_TEMPLATE/falsification-evidence.md)

### 6. Documentation Improvements

Enhance clarity and accessibility:

- **Typo fixes** and grammatical corrections
- **Clarifying explanations** of complex concepts
- **Additional examples** or diagrams
- **Better cross-references** between sections
- **Translations** to other languages

**Use**: Standard pull request (no template needed)

## Contribution Workflow

### For Issues (Questions, Discussions, Proposals)

1. **Search existing issues** to avoid duplicates
2. **Choose the appropriate template** from [.github/ISSUE_TEMPLATE](.github/ISSUE_TEMPLATE/)
3. **Fill out all required sections** with as much detail as possible
4. **Use clear, descriptive titles** (e.g., "Hyperscanning prediction: fMRI coupling in meditation" not "Question about Field")
5. **Add relevant labels** if you have permission
6. **Engage constructively** with feedback and questions

### For Pull Requests (Direct Contributions)

1. **Fork the repository** to your own GitHub account
2. **Create a feature branch** from `main` (e.g., `feature/improve-glossary`)
3. **Make your changes** following [style guidelines](#style-guidelines)
4. **Test cross-references** to ensure all links work
5. **Update CHANGELOG.md** if making significant changes
6. **Submit a pull request** using the [PR template](.github/PULL_REQUEST_TEMPLATE.md)
7. **Respond to review feedback** promptly and constructively

### For Major Contributions

If you're planning a substantial contribution (e.g., new theoretical section, major experimental protocol):

1. **Open an issue first** to discuss the proposal
2. **Get feedback** from maintainers and community
3. **Coordinate** to avoid duplicate work
4. **Proceed** with pull request once approach is agreed upon

## Pull Request Process

1. **Use the PR template**: Fill out all sections in [.github/PULL_REQUEST_TEMPLATE.md](.github/PULL_REQUEST_TEMPLATE.md)

2. **Ensure your PR**:
   - Addresses a specific issue or improvement
   - Maintains consistent formatting with existing documents
   - Includes proper cross-references
   - Updates relevant sections (e.g., glossary if new terms introduced)
   - Passes all automated checks (if any)

3. **PR Review**:
   - Maintainers will review within 1-2 weeks
   - Address feedback promptly
   - Make requested changes via additional commits
   - Once approved, maintainers will merge

4. **After Merge**:
   - Your contribution will be acknowledged in CHANGELOG.md
   - Significant contributions may be highlighted in the README

## Code of Conduct

### Our Pledge

We are committed to providing a welcoming, inclusive, and harassment-free experience for everyone, regardless of:
- Background or identity
- Level of experience or education
- Discipline or field of expertise
- Geographic location
- Native language

### Expected Behavior

- **Be respectful**: Value diverse perspectives and experiences
- **Be constructive**: Focus on ideas, not people; critique arguments, not individuals
- **Be collaborative**: Share credit; acknowledge prior work and contributions
- **Be precise**: Use operational definitions; distinguish speculation from evidence
- **Be open**: Welcome challenges to your ideas; update views based on evidence

### Unacceptable Behavior

- **Personal attacks**: Ad hominem arguments, insults, or harassment
- **Dismissiveness**: Rejecting ideas based on author credentials rather than merit
- **Dogmatism**: Refusing to engage with evidence or alternative views
- **Plagiarism**: Failing to credit sources or prior work
- **Trolling**: Bad-faith arguments or deliberate disruption

### Enforcement

Violations will result in:
1. **First offense**: Warning from maintainers
2. **Second offense**: Temporary ban (1 month)
3. **Third offense**: Permanent ban

Report violations to maintainers via private message or email.

## Style Guidelines

### Markdown Formatting

- **Headings**: Use sentence case (capitalize first word only)
- **Lists**: Use `-` for unordered lists, `1.` for ordered lists
- **Emphasis**: Use `**bold**` for key terms on first use, `*italics*` for emphasis
- **Code**: Use `backticks` for technical terms, file names, or code snippets
- **Links**: Use descriptive text, not "click here" or bare URLs

### Cross-References

Use relative links to connect related sections:

```markdown
The [Field layer](../theory/field-layer.md) provides substrate-independent coupling. See [glossary](../docs/glossary.md#field) for the operational definition.
```

### Operational Definitions

When introducing new concepts:
1. **Define operationally**: Specify measurable criteria
2. **Distinguish clearly**: Explain what the concept is NOT
3. **Provide examples**: Include both positive and negative cases
4. **Add to glossary**: Update [docs/glossary.md](docs/glossary.md)

### Academic Style

- **Cite sources**: Include references in [CITATIONS.md](CITATIONS.md)
- **Be precise**: Avoid vague language (e.g., "may" vs. "will" vs. "must")
- **Acknowledge uncertainty**: Distinguish established facts from speculations
- **Use evidence**: Support claims with data, not just intuition

### Document Structure

Each document should include:

1. **Breadcrumb navigation** at the top:
   ```markdown
   [Home](../README.md) > [Theory](README.md) > Field Layer
   ```

2. **Table of contents** for documents >500 words

3. **Related sections** at the bottom:
   ```markdown
   ## Related Sections
   - [Node Layer](node-layer.md)
   - [Integration](integration.md)
   - [Glossary: Field](../docs/glossary.md#field)
   ```
